The user's checkout was clean at `096ca75`, one commit behind; the newer commit
adds optional private tileset fetching. Review work is on

**Recommendation:** keep the pixel office and existing React/Pixi/Zustand stack.
First repair the privacy boundary and ingestion correctness, then add real Codex

does not implement the fixes or replace the running product UI.

## Findings, in priority order

P1 means fix before relying on the relevant privacy/correctness guarantee.
P2 means material reliability or workflow debt worth addressing in the next work.

### 1. P1: browser snapshots and adapters expose sensitive content

[`SessionManager.getSnapshot`](../../server/session-manager.ts), lines 597-602,
spreads the internal agent object. `registerSession` puts `filePath` on that
object, so every snapshot includes the full transcript path. Returning the
TypeScript type `Agent[]` does not remove runtime properties.

Synthetic probe result:

```text
filePath: C:/Users/example/.claude/projects/C--private-client/session.jsonl
project: private-client
```

[`codex-notify.js`](../../server/hooks/codex-notify.js), lines 32-35, takes the
first 80 characters of `last-assistant-message`. A synthetic private-response
marker reached the browser as `activityText`. Truncating a response is not
redaction. The Claude adapter also passes through search patterns and freeform
tool descriptions; a synthetic secret search string appeared in an outgoing
Grep event. See [`claude-adapter.ts`](../../server/bridge/claude-adapter.ts),
`extractSafeContext`.

**Change:** serialize an explicit public snapshot shape and replace freeform
assistant/search/command text with allowlisted descriptions. Keep useful safe
metadata such as provider, state, tool category, and carefully derived basename.
Add regression assertions over both event and snapshot payloads. This is one
privacy-boundary workstream, not merely a Codex string fix.

### 2. P1: the shared token does not authenticate viewers

[`server/index.ts`](../../server/index.ts), lines 86-104, injects `JOBS_TOKEN`
into HTML served to unauthenticated visitors. A probe fetched `/`, extracted
the synthetic token, connected to `/ws`, and received a snapshot. `/api/stats`
also returned 200 without credentials. Anyone able to reach the app can obtain
the credential, including the token used for `/api/hooks`.

Generic webhooks use a separate optional `WEBHOOK_TOKEN`. Setting only
`JOBS_TOKEN` leaves that ingestion endpoint open. In addition, the checked-in
Compose environment does not pass either token; adding them only to Compose's
`.env` does not by itself inject them into the running service. See
[`docker-compose.yml`](../../docker-compose.yml) and
[`webhook-receiver.ts`](../../server/webhook-receiver.ts).

**Change:** define and enforce a coherent viewer/ingestion authentication model
across HTML, stats, WebSocket, hooks, and webhooks. An authenticated reverse
proxy is a viable deployment option if it covers all intended routes; explicit
application login/token entry is another. Keep health identity deliberately
minimal. Pass configured credentials into Compose explicitly. Replace the
README's blanket network-safety claim with verified setup requirements.

### 3. P1: Unicode breaks JSONL byte offsets and replays events

[`watcher.ts`](../../server/bridge/watcher.ts), lines 147-163, decodes a buffer,
finds the newline in a JavaScript string, then adds that character index to a
byte offset. Those units differ for non-ASCII text.

A fixture containing emoji followed by a tool record stored offset `2043`
for `4043` consumed bytes. After the next append, it emitted an invalid fragment
and replayed `tool-A` before emitting `tool-B`. Replayed tools inflate counts and
can repeat lifecycle transitions.

**Change:** find complete records and advance offsets in bytes; decode only the
complete byte slice. Add Unicode, partial-write, truncation, and per-file
serialization checks. The Unicode replay was reproduced directly against the
compiled watcher; concurrent filesystem delivery remains a separate stress case.

### 4. P2: desk allocation still uses the old five-seat capacity

[`src/types/agent.ts`](../../src/types/agent.ts) initializes six desks. The server
reserves the last for supervision, leaving five regular assignments.
[`PixelOffice.tsx`](../../src/engine/PixelOffice.tsx) installs sixteen regular
desks plus a supervisor desk only in the browser. The server never receives
that map configuration.

Nine synthetic agents received `[0, 1, 2, 3, 4, null, null, null, null]`.
This explains why additional agents can lack assigned desks despite visible
space. Merely recalculating client target coordinates cannot create allocations.

**Change:** select and share one layout configuration before server allocation
and client rendering. Test capacity and fallback behavior for each layout.

### 5. P2: resumed webhook agents can be deleted by an earlier stop

[`removeWebhookAgent`](../../server/session-manager.ts), lines 685-707, schedules
unconditional deletion by ID after two seconds. Updating that agent to running
during the delay does not cancel removal. The probe resumed it immediately and
found it gone after 2.1 seconds. A repeated `start` also returns the existing
object without restoring its state. The separate session-ended timer deserves
the same generation-aware treatment.

**Change:** make start/stop idempotent, cancel stale removals, and verify both
generation and current state before deleting an agent or releasing its resources.

### 6. P2: Codex completion does not participate in input-needed UX

The notifier maps completion to `waiting`, but webhook registration sets
`waitingForHuman: false`, and applying the state never changes it. A real
notifier invocation with a synthetic payload produced exactly that combination.
The roster's `NEEDS INPUT` badge, waiting-first ordering, and browser
notifications depend on the boolean, so Codex misses those features.

**Change:** distinguish turn completion, input needed, idle, and disconnected
states in the normalized lifecycle. Set and clear the same canonical fields for
all providers, and test the resulting roster and notification behavior.

### 7. P2: snapshot removal bypasses client cleanup

[`useOfficeStore.handleSnapshot`](../../src/state/useOfficeStore.ts), lines
202-249, replaces the roster but retains entries in per-agent tracking maps and
does not clear selection/follow state for missing agents. The probe ended with
zero agents, one retained history, and the old followed-agent ID. Webhook and
stale removals commonly arrive through snapshots.

**Change:** reconcile removed IDs through common cleanup, covering histories,
tool counters/timers, selected/focused/followed IDs, and pending removals. Also
initialize history for agents first introduced by a snapshot. Otherwise a newly
connected viewer's duration/timeline is incomplete even for an active session.

### 8. P2: CI's security gate allows the current high-severity backlog

The live npm audit reports high entries for brace-expansion, browserslist,
concurrently, js-yaml, nanoid, postcss, and shell-quote. These are dependency
entries, not seven independently confirmed exploitable application bugs.
The production-only graph has five moderate entries. The Dockerfile currently
copies the full build `node_modules` directory, including development packages.

**Change:** triage narrow dependency groups and make `high` the intended gate if
that matches the project's policy. Prune/install production dependencies for the
runtime image. Assess actual call paths before major upgrades: npm proposes a
major `uuid` upgrade, while this repo's event factory uses v4. Do not run a broad
`audit fix --force` as routine cleanup.

## Codex feature review

### What currently works

The notify script registers a stable `wh:codex-<thread>` agent after completion,
uses a basename for its project, and sets `provider: codex`. The roster badge,
robot mascot, selection, and follow infrastructure understand that provider.
Generic webhook state changes can move it around the office.

The actual Codex source only supplies completion updates. It does not provide
turn start, tool calls, approval waits, compaction, child relationships, usage,
or a reliable session end. Tool charts and the activity feed are therefore not
equivalent to Claude's event-based view. Multiple sessions are all named
`Codex CLI`; the thread identity is present but hard to distinguish in the UI.
This limitation was acknowledged as turn-level granularity in `VISION.md`,
but is easy to miss from the README's general support claim.

The current `notify` documentation still describes only `agent-turn-complete`.
Keep this as a minimal compatibility mode with a clear capability label.
[Official notification documentation](https://learn.chatgpt.com/docs/config-file/config-advanced#notifications).

### Best next integration

**Use a provider adapter around supported lifecycle hooks for passive monitoring.**
Current Codex docs expose session, prompt, tool, approval, compaction, subagent,
stop, and interruption events. They accept stdin JSON and can run command hooks
asynchronously; session-end delivery remains synchronous. Hooks require trust
review. Hosted search is not covered by local tool hooks, and background delivery
can finish out of order. These are documented capabilities, not an end-to-end
validation of every installed Codex surface.
[Official Codex hooks documentation](https://learn.chatgpt.com/docs/hooks).

Start with session start, prompt submission, tool start/end, stop, and session
end. Normalize provider/session/turn/tool IDs, safe activity categories, and
timestamps before feeding the existing state machine. Add approval, compaction,
and explicit parent/child relationships next. Use event deduplication and
ordering so late updates cannot revive a completed turn. Treat unsupported
capabilities as unavailable instead of showing invented activity or zero metrics.

Do not send Codex hooks straight to the existing Claude hook path: session
registration there assumes Claude, and its accepted event names/state handling
do not fully match Codex. Build a provider-specific adapter first.

App-server is useful if JOBS later owns or explicitly connects to a Codex runtime:
it provides streamed thread/turn/item state and richer approval/history APIs.
It is not automatically a global event feed for unrelated running Codex clients.
Evaluate the attachment/ownership model before choosing it for this passive app.
[Official app-server documentation](https://learn.chatgpt.com/docs/app-server).

Transcript watching would preserve the zero-config theme but introduces another
format-sensitive parser and more sensitive content handling. Current hook docs
explicitly call the transcript format unstable. Prefer hooks where available;
if transcripts become a fallback, isolate the adapter and pin compatibility
fixtures to tested versions. [Hook input documentation](https://learn.chatgpt.com/docs/hooks#common-input-fields).

### Setup and diagnostics

The setup script hardcodes `~/.codex/config.toml`, replaces an existing `notify`
command, and edits TOML line by line. Multiline values and pre-existing tools
need preservation. A custom `CODEX_HOME` would be missed. Review rather than run
the existing installer against a real configuration.

A revised installer should support an explicit config home, dry-run, backup,
idempotent install/remove, preservation of unrelated hooks, and a synthetic
delivery test. Show provider connection health, last event time, delivery mode,
and known limitations in the app. Keep credentials out of diagnostic output.
User-level location matters for legacy `notify`; current docs disallow overriding
that key through project-local config.
[Official configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

## UI/UX review and modern direction

**Keep the office playful; make the surrounding application calm and readable.**
The strongest visual identity is already the pixel scene and mascots. The main
usability problem is the overlay composition and information hierarchy.

| Observed problem | Proposed change |
| --- | --- |
| Roster text measures 10.88px; activity/time labels are smaller and faint | 14-16px primary UI, at least 12px secondary metadata, stronger contrast |
| Header controls are about 24px tall; follow buttons about 15px | Comfortable controls, with 44px touch targets for primary mobile actions |
| `SFX`, `D/N`, `NOTIF`, theme cycling compete across the header | One settings surface with named options; keep connection health visible |
| Roster position shifts with the presence of feed/groups | Stable sidebar and a dedicated activity region |
| No first-class attention queue | `Needs input`/errors first; filters for project, provider, and status |
| Code and project context truncate early | Two-line session rows: task/project first, provider/state/time second |
| Detail and stats cover the office | Reserved inspector space on desktop; intentional sheet/page on narrow screens |
| At 390px, header right edge reaches 404.8px | Responsive header and mobile navigation rather than squeezing every toggle |
| Mobile canvas stretches a 4:3 scene to roughly 366x820 | Preserve the scene aspect ratio; fit/zoom/pan intentionally |
| Agent/group clicks use non-focusable `div`s | Real buttons, keyboard selection, named close actions, Escape and focus return |
| No reduced-motion CSS handling | Apply motion preference to CSS effects and Pixi ambience/follow movement |
| Empty text only says it is watching Claude | Explain connected providers, waiting for activity, and how to try demo/setup |
| Five raw event strings with little context | A readable timestamped activity log with filtering and pause/expand controls |

The mobile defects were visible with both the fallback and Tiled renderer. The
Tiled production page itself rendered successfully under the existing CSP.
Missing accessible state and semantic controls matter more than adding ARIA
labels indiscriminately: text buttons already have names, while the clickable
roster rows have no keyboard role or focus target.

The detail panel calls its value duration, but it derives its start from local
history (or the most recent event). The roster's purported uptime is time since
the last event. Label those values honestly and supply authoritative session
start time for session duration. `Today` in server stats uses UTC; make the
reporting timezone explicit. Stale eviction also leaves stats sessions open, so
aggregate hours should be treated cautiously until lifecycle accounting is fixed.

### Design concept

Open [the interactive concept](2026-09-07-ui-concept.html). It is a standalone
HTML proposal with synthetic sessions, search/provider/attention filters,
selectable agents, an inspector, settings, and an office/list switch. It is not
connected to the backend and does not require paid tiles or external fonts.

- Palette: midnight `#151d2b`, slate `#1d293a`, edge `#33455e`, text `#eef3fb`,
  sky `#79b8ef`, amber `#efb75b`. Color communicates state and selection.
- Type: Segoe UI/system sans for controls and descriptions; monospace for the
  J.O.B.S. wordmark and technical identifiers. Keep the office itself pixelated.
- Desktop: fixed header, session rail, central office/activity area, inspector.
- Narrow screens: stack these regions with navigation and focus management;
  keep session actions available independently of the canvas.
- Motion: response to selection/follow is useful; constant HUD animation is not.

This direction also advances the existing Settings Menu, Demo Mode, Keyboard
Shortcuts, and Kiosk Mode ideas in `VISION.md`. A separate kiosk mode can emphasize
the full office without forcing that composition on everyday session management.

## Suggested implementation sequence

1. **Privacy and access boundary:** public serializers, safe provider payloads,
   coherent auth/Compose configuration, focused privacy and unauthenticated-access checks.
2. **State correctness:** byte-based watcher offsets, shared map capacity,
   lifecycle cancellation, snapshot cleanup, authoritative timing/stats.
3. **Codex monitoring:** safe provider adapter, supported lifecycle hooks,
   non-destructive installer and delivery diagnostics, capability-aware UI.
4. **Modern application shell:** stable layout, readable session rows, attention
   queue, settings, responsive inspector, keyboard/reduced-motion behavior.
5. **Polish and release:** provider docs, accessible demo/empty/disconnected
   states, production CSP and asset fallback checks, narrow dependency remediation.

Each step can be a focused PR. The UI shell can proceed independently once its
state contract is agreed; it need not wait for every integration feature.
